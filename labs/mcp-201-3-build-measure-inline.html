Phase 1

Start a tool of your own

In this phase, you'll create the skill, say what it accepts, and give it the description you wrote.

Pattern

One job per tool

A tool is built around what someone is trying to get done, not around whatever calls the expense API happens to offer.

1.1

Get a blank tool of your own

Noor's expense went wrong in Lab 1 because seven separate tools left the assistant to decide the order. The tool you sketched on paper in Lab 2 takes that decision back. It starts here, as an empty skill in your own project.

Overview

You end with a new skill named submit_expense_report, its callable trigger selected, and the six inputs from your handout declared. The old fragmented skills stay exactly where they are — this is a second tool alongside them, not a repair of the first.

Heads up

Two tools can share a name, and that is fine here

Your project already contains a submit_expense_report from the fragmented server. Workato lets a second skill take the same name, and the two never meet: each one is exposed by a different server, and a conversation only ever has one server attached.

Detailed steps 7 steps

Declaring the inputs first fixes what the caller is allowed to hand you, which is the same thing as fixing what the caller can get wrong.

  • In your project, select Create and then Skill.
  • Name the skill submit_expense_report, confirm the location is your own project, and select Start building.
  • On the trigger step, choose the Workato Skill app and the Start workflow event.

  • Select Save.
Verify the trigger declares six inputs and three result fields, and that no input asks the caller for a department or a policy decision.
1.2

Tell the model when to call you

Four lines decide whether this tool is ever called. A model reads them before it has seen a single input field, and whatever they leave out, it guesses.

Overview

You end with the trigger's Description carrying your own four lines from the description table: when to use it, when not to and where to go instead, what it handles for itself, and where it stops. Type what you wrote, not a tidier version of it.

Detailed steps 5 steps

Carrying your own words across from paper keeps the design and the build the same piece of work, rather than two things that happen to sit near each other.

  • Open the description table on your handout.
  • Open the trigger step and find the Description field.
  • Type your four lines, keeping the alternative tool named exactly as it appears on your handout.
  • Read it back once as if you were the model, and cut any sentence that only repeats an input name.
  • Select Save.
Verify the description says when to use the tool, when not to, names get_expense_report_status as the alternative, lists what runs inside, and states a limit.
Phase 2

Put the checks inside

In this phase, you'll wire the employee lookup, both checks, and the write in the order you decided.

Pattern

Check before you write

Each check runs on a value the step before it returned, and answers before anything is created. A check the model is allowed to skip is a check that gets skipped.

2.1

Find out who is filing

In Lab 1 the assistant was asked which department to bill. It read EMP-0005, answered DEPT-0005, and no such department exists — so the check that followed was answered perfectly about a department nobody has.

Overview

You end with Get employee as the first action, taking employee_id straight from the trigger. Its department_id output is the value both of your checks will use, and it is the reason neither of them has to ask the caller for a department.

Note

Let AIRO wire it, then check its work

Ask AIRO in the recipe editor will build steps from a description of what you want. Give it your step order and let it draft. Then read what it produced against your own handout, because the assistant building your recipe can make the same mistake the assistant filing the expense made — reaching for a department it worked out for itself instead of the one the lookup returned.

Detailed steps 5 steps

One step consuming another step's output is what turns a suggested order into an order that cannot be skipped.

  • Under ACTIONS, select +, choose the Roster (HR) connection, and add Get employee.
  • Map Employee ID from the trigger's employee_id.
  • Open the step's output list and find department_id and status.
  • If you used Ask AIRO to draft this step, open it and confirm the employee ID came from the trigger rather than from a value AIRO wrote in itself.
  • Select Save.
Verify Get employee is the first action, its input traces to the trigger, and its output list shows a department_id you can map from later.
2.2

Stop the over-limit expense before it exists

The upgraded room costs $347 against a 300 USD lodging limit. In Lab 1 the tool that would have caught it was sitting right there on the server, and the assistant filed the expense without calling it.

Overview

You end with Check policy limits running before anything is written, taking its department from Get employee and its category and amount from the request. When it comes back non-compliant, the tool answers rejected_policy and stops, so the create step below it never runs.

Heads up

Returning a response does not end the run

Return response sends an answer back to the caller and then carries straight on to the next step. Without a Stop job after it, your recipe can hand back a rejection and create the expense report anyway — a green run, an honest-looking rejection, and a report in the list anyway.

Detailed steps 9 steps

This is the shape you will build once and use again in the next task: a check, a decision, an answer, and a stop.

  • Add Check policy limits from the Rebate (Expense) connection as the next action.
  • Map Department ID from Get employee → department_id, not from the request.
  • Map the line's Category ID and Amount from the trigger.
  • Add an IF on Check policy limits → Compliant equals false.
  • Inside it, add Return response and set outcome to rejected_policy.
  • Build the message from the step's own output so it names the amount, the allowed limit, and that no report was created.
  • Add Stop job straight after the response and set Stop with error to No.
  • Follow the rejection path down the canvas and confirm it cannot reach Create expense report.
  • Select Save.
Verify the non-compliant path reads Check policy limits → IF → Return response → Stop job, returns rejected_policy with the limit taken from the check rather than typed in, and ends above the create step.

Catch a budget code that does not belong

CC-4400 is the People and Culture cost centre and Noor is in Engineering. BAD-999 is not a cost centre at all. Neither should reach a report, and the check that tells them apart needs the same department the policy check already used.

Overview

You end with Validate budget code running only when the request carried one, reusing department_id from Get employee, and rejecting with rejected_budget in the same shape you built in the last task. Requests with no budget code carry on to the write.

A check that only applies sometimes still has to be impossible to skip when it does apply, which is what the surrounding condition is for. ▲ Reuse the department from Get employee. Deriving DEPT-0005 from EMP-0005 is the exact mistake you diagnosed in Lab 1, and the budget check will answer it perfectly for a department nobody has.

  • Add an IF on Trigger → budget_code is present.
  • Inside it, add Validate budget code from the Rebate (Expense) connection.
  • Map Department ID from Get employee → department_id and Budget code from the trigger.
  • Add a second IF on Validate budget code → Valid equals false.
  • Inside that, add Return response with outcome set to rejected_budget and a message that names the code and says no report was created.
  • Add Stop job after it with Stop with error set to No.
  • Select Save.
Verify the budget check runs only when a code was supplied, takes its department from Get employee, and its rejection ends before the create step.
2.4

Finish the job instead of leaving a draft

In Lab 1 the valid $245 expense came back as a success three times out of four, and three times out of four it was still sitting in draft. The assistant said so, offered to submit it, and nobody noticed.

Overview

You end with Create expense report and Submit expense report running one after the other, and a final Return response carrying filed and the report ID. Creating is not filing, and the caller has no way to tell the difference from the response alone.

Detailed steps 7 steps

Putting both writes inside one command is what makes "filed" mean filed, rather than "the first half worked".

  • Below both rejection branches, add Create expense report from the Rebate (Expense) connection.
  • Map employee, purpose, and the line's category, amount, and date from the trigger.
  • Add Submit expense report and map its Report ID from Create expense report → report_id.
  • Add a final Return response with outcome set to filed, the report ID, and a short message.
  • Read the whole recipe from top to bottom against the step table on your handout, and answer the question it asks of every step: does every check run before anything is written?
  • Confirm both rejection branches end in a Stop job and neither one can fall through to the create step.
  • Select Save, then Exit and start the recipe.
Verify create and submit run in that order in the same recipe, the final response returns filed with a report ID, and no path reaches create without passing both checks.
Phase 3

Put it where your assistant can reach it

In this phase, you'll expose the tool on its own server and connect that server in LibreChat.

Pattern

Keep the status tool separate

Submission stays one command. Reading a report's status stays its own tool, because it is useful on its own.

3.1

Hand your assistant two tools instead of seven

Your tool exists but nothing can call it yet. Noor's assistant reaches Workato through an MCP (Model Context Protocol) server, and the one it has been using all morning is the fragmented seven.

Overview

You end with a second MCP server in the same project carrying exactly two tools — your composed submission command and get_expense_report_status — connected in LibreChat and answering in a fresh conversation. The fragmented server stays exactly as it was.

A second server keeps Lab 1's readings meaningful: the comparison in the next phase only works while both designs still exist to be run. ▲ The generated MCP Server URL embeds your token, so outside this lab treat it the way you would treat a password.   • Open a fresh conversation and attach only your new Process server.
  • Ask What tools do you have available? and confirm exactly two tools are listed.
Verify exactly one server is attached in LibreChat, it reports a connected state, and the assistant lists your submission tool and the status tool and nothing else.
Phase 4

Prove it and compare

In this phase, you'll send the four requests and record what each one did, next to your Lab 1 readings.

Pattern

Same prompt, fresh conversation

Use the same model, the same client, and the same wording, in a new conversation each time. Report each request on its own — three runs are not a sample you can average.

4.1

Try both sides of the decision

Your tool has to accept one request and reject two. Passing only the rejections would prove nothing more than a tool that rejects everything — and the fourth request is the one you chose yourself.

Overview

Requests 1, 2 and 3 are the scored ones: the first must come back filed, the second and third rejected_policy. Request 4 is your own wording from Lab 1, run against the other design. Send each in a new conversation with only your Process server attached.

Heads up

The response is a claim; the expense application is the evidence

Mark a request correct only when the outcome word and the expense application agree. A tool can say rejected_policy and still have written something. If you cannot reach the expense application, stop checking outcomes rather than take the response at its word.

Detailed steps 8 steps

All three together test both sides of the decision and the promise that nothing was written.

  • Open 1 · Valid expense, start a fresh Process-only conversation, and send the tab's exact wording.
  • Carry the conversation to its final answer, then check for filed and exactly one matching report in the list.
  • Record the time, the number of tool calls your assistant made, and the business result, and note the matching Workato job.
  • Repeat in a new Process-only conversation for 2 · Over-limit expense, and check for rejected_policy with no matching report.
  • Repeat again for 3 · Policy-bypass attempt, and check for rejected_policy with no matching report.
  • Open 4 · Your prompt, which carries the wording you settled on in Lab 1, and send it in one more fresh Process-only conversation.
  • Record its readings too, and note which difference you can put down to the design rather than to the run.
  • Keep every first run, including one that went wrong.
Verify request 1 is filed with a report present, and requests 2 and 3 are both rejected_policy with no report. All three must pass.
4.2

Compare the designs without pooling them

Fewer tool calls only matter once the process did the right thing. The four requests take different paths through your tool, so each one needs its own conclusion.

Overview

You end with all four requests complete in the Fragmented-versus-Process workbook, with filed and rejected_policy visible. Your prompt carries the wording you wrote in Lab 1, so it is a fair pair even though nobody else in the room ran it.

Detailed steps 5 steps

Keeping each request separate preserves the link between doing the right thing and doing it cheaply, without turning three different paths into one number. ▲ Do not calculate a median, pool the rows, or claim overall server performance. Report what happened, the calls, and the time for each request on its own.

  • Review all four tabs from Task 4.1; your Lab 1 readings stay read-only on the left.
  • For each request, say whether it did the right thing first, then the number of tool calls, then the time.
  • For fragmented requests 1 and 3, keep correct this run separate from guaranteed by the server.
  • For fragmented request 2, keep needs_approval if that is what you saw, and say why a written over-limit report still fails the promise that nothing is created.
  • For Your prompt, say whether the redesign changed its result, and if it did not, what would have to change instead.
Verify all four rows are complete, what happened is reported before the calls and the time, no average or median appears, and the three scored rows all pass.

Bonus challenges

Your tool now handles the three failures you diagnosed in Lab 1. The complete version handles more, and a reference build is available to compare against once you have your own working — read it after, not before.

  • Say what actually happened. Submitting a report can come back submitted or needs_approval. Your tool reports filed either way. Return filed_pending_approval when the application says approval is pending, and see whether the assistant's summary changes.
  • Handle the check that did not run. The policy action fails open: a department with no limits set returns policy_check_skipped rather than an error, and your condition reads that as a pass. Decide what your tool should do about a check that did not happen, and build it.
  • Turn "lodging" into a category. The tool needs CAT-0002 and a person says "lodging". Add the catalog lookup, reject unknown categories with rejected_category, and hand the valid set back in the message.
  • Decide who may file. Filing on the CEO's behalf still works. Nothing in this system records who is asking, so ordering the checks cannot fix it. Write down what would have to exist before it could be.
  • Translate the errors. Every application error arrives as a bare Tool execution failed. Wrap the writes in error monitoring and return error_upstream with something a caller could act on.
  • Let AIRO do the tedious parts. The branches above are repetitive. Describe one to Ask AIRO, then check what it built the same way you checked its first draft.

If you get stuck

  • A rejection still creates a report. Stop testing and check for the Stop job after your Return response.
  • The policy check rejects everything, including the $245 request. Open the step and confirm the department came from Get employee rather than from the request.
  • A connector action or field differs from this guide. Write down the step number and the label you actually see, then ask — do not guess.
  • Both servers are attached in LibreChat. Detach one and send that request again in a new conversation.
  • AIRO replaced your description. It writes its own when it builds the trigger. Paste your four lines back in.
  • You want to start a section over. Ask for the reference build, copy the part you are stuck on, then carry on in your own recipe.

Reflect

Now that one tool has been tested against a valid request and two that break policy, consider what the evidence can and cannot settle.

  • Which piece of evidence showed that a rejection stopped the write, rather than only describing one?
  • Why does request 1 have to pass before the two rejections mean anything?
  • What is still missing when someone asks to file for the CEO, and why did putting the checks inside not add it?
  • Why does a smaller number of tool calls in the conversation not mean fewer steps ran inside the recipe?
  • Which part of this design belongs in the tool description, and which part has to be in the recipe where nothing can talk it out of running?

Wrap-up

Noor's valid expense filed, while both policy-breaking requests were stopped before anything was created, as long as the expense application agreed every time.

  • One job per tool. Submission owns the checks it needs; reading a status stays its own tool.
  • Check before you write. The employee lookup supplies the department, and both checks answer before the create step exists.
  • Answers that mean something. rejected_policy says what was over, by how much, and that nothing was created.
  • What happened before how fast. Each request reports its business result before its calls and time, with no pooled claim.

Keep the recipe as it is for the debrief.
