Redesign the tools

Intermediate 35 minutes Lab 2 of 3
Introduction

In this lab, you'll act as an integration engineer for IDEA Brands, turning the seven scattered expense tools you watched in Lab 1 into one command that files an expense properly. The handout in front of you is the lab. Every task sends you to one table on it, and what you write there is what you build in Lab 3.

Noor Aziz
Software Engineer · IDEA Brands

They file a hotel expense at $347 a night, the assistant reports it as submitted, and the policy check that would have caught the rate never ran.

The question

What would this tool have to say about itself for the model to have no room left to get it wrong?

You'll learn how to

  • Choose the tools one submission needs and the order they have to run in

Phase 1

Decide what belongs inside

In this phase, you'll choose the tools one submission needs and the order they have to run in.

Pattern

One job per tool

A tool is built around what someone is trying to get done, not around whatever calls the API happens to offer.

1.1

Read your Lab 1 runs back as evidence

Your Lab 1 workbook holds four runs, and at least one of them came out right while still leaving a check entirely up to the model. That gap, between an answer that was right and one you could rely on, is why this lab exists.

Overview

The runs table on your handout, filled in for all four runs, from 1 · Valid $245 lodging through 4 · Your own prompt. Your Lab 1 workbook and conversations are the source. The last column is the one that matters: what the design left the model free to choose, not how the run happened to turn out.

Detailed steps 4 steps

Four runs you actually watched keep the rest of this honest. When you are not sure whether something belongs inside the tool, you can go back and look at what happened.

  • Open your Lab 1 workbook and the conversations you kept, and take the four runs one at a time.
  • On the runs table, record whether the business outcome was right for each run.
  • Write where it went wrong, or where it could have gone wrong with nothing there to stop it. Your prediction for your own prompt belongs in this column too.
  • In the last column, name what the design left the model free to decide for itself. The rest of this lab builds on that column.
Verify the runs table has a row for every Lab 1 run, and that the last column names something the model was free to choose rather than repeating the result.
1.2

Put the tools in the order a submission needs

The old server has seven tools because someone gave each API call a tool of its own. Noor is not trying to validate a budget code. They are trying to file a hotel expense.

Overview

The order table, numbered. Each row ends up one of two ways: a number saying when that tool runs and what breaks if it runs later, or no number and the reason a submission does not need it. A blank row is still a decision, so a blank reason reads as a row you skipped.

Key insight

Composition is not consolidation

It is easy to go too far here. Pulling the checks that one job needs inside a single command is the point, because then the model cannot skip them. Putting everything expense-related inside one tool is not: something that files, cancels, updates and reports status is several tools wearing one name, and the model is back to working out which of them it wants.

Detailed steps 6 steps

The order you write here is what you build in Lab 3, so everything after this follows from it.

  • On the order table, read the seven tools the old server offers.
  • Number the tools a submission needs, in the order they have to run.
  • Leave the Order cell empty for every tool that is useful on its own.
  • For each numbered row, write what goes wrong if that tool runs later than its number.
  • For each empty row, write why a submission does not need it.
  • Under the table, name one tool that needs another tool's answer first, and what you saw when the model ran both at once.
Verify the order table numbers only the tools a submission needs, in the order they run, and gives a reason on every row — numbered or not.
Phase 2

Write the contract

In this phase, you'll write down the job, the inputs, the steps inside, and what the model reads.

Pattern

Four-part description

When to use it, when not to and where to go instead, what it handles for itself, and where it stops. A description that only lists the inputs tells the model nothing it could not already see.

2.1

Say what the one job is, and cut the inputs

The old design asked the model which department to bill. It read employee EMP-0005, answered DEPT-0005, and no such department exists — so the budget check that followed was answered perfectly, about a department nobody has.

Overview

The one-job table complete: the one job in a single sentence beginning "Submit", and the printed list of inputs marked up so anything a caller would have to guess at is crossed out, with your reason beside it. Watch for codes — the category input wants something like CAT-0002, but a person says "lodging".

Detailed steps 5 steps

Every input you take away is one more thing the model cannot get wrong, because the tool now looks that value up itself.

  • On the one-job table, write the one job as a single sentence beginning with "Submit".
  • Read the list of inputs printed on this handout, and take them one at a time.
  • Cross out every input that asks the caller for something it cannot know, and write beside it what you stopped it deciding.
  • Notice which value is missing from that list, and write down where your tool gets it instead.
  • Write down who turns a word like "lodging" into a category code — the caller, or the tool.
Verify the one-job table states one job in one sentence, and that no input left standing asks the caller to make a policy decision or name a department.
2.2

Make each step say what it decides and returns

Someone told Tool execution failed. and nothing else cannot tell whether an expense report now exists. Noor's next move, trying again or waiting for an approval already on its way, depends entirely on which it is.

Overview

The step table, carrying the order you set, and for each step: what it decides, what it says back when it fails, and whether a report exists by then. Spell the four rejection words exactly as they are printed, because Lab 3 looks for them letter for letter.

Detailed steps 6 steps

Writing each answer next to the step that produces it is what turns your ordering into something you can test.

  • Copy your numbered order into the Step column of the step table.
  • For each step, write what it decides.
  • For each step, write what it says back when it fails, using rejected_policy, rejected_budget, rejected_category, and rejected_ineligible exactly as spelled.
  • For each step, mark Y or N for whether a report exists by the time that answer comes back.
  • In the last three rows, write what someone learns from filed, filed_pending_approval, and error_upstream, and what to do next in each case.
  • Read the note under the table, then act on every Y you marked.
Verify the step table carries the order you set, spells the four rejection words exactly, answers the report column on every step, and settles every Y.
2.3

Tell the model when not to call you

These four lines are everything the model reads before it decides whether to call your tool. Four lines that only repeat the input names tell it nothing it could not already see.

Overview

All four rows of the description table written: when to use it, when not to, what the tool handles for itself, and where it stops. They have to be clear enough that someone else could type them into Lab 3 exactly as they stand.

Detailed steps 5 steps

The model reads this before it calls anything, so whatever these four lines leave out, it has to guess.

  • On the description table, write when to use the tool, describing the situation someone is in rather than the operation it performs.
  • Write when not to use it, and name the status tool as where to go instead.
  • List what the tool handles for itself, taking it from the step table.
  • Write the tool's limits, and what it will not decide.
  • Read the four rows back together, and check that someone could type them into Lab 3 without asking you what you meant.
Verify the description table says when to use the tool, when not to, names the alternative, lists what it handles for itself, and says where it stops.
Phase 3

Check it routes

In this phase, you'll read your description back against two requests that have to go different ways.

Pattern

Reading it back

A description is only as good as the choices it leads a model to make, and reading it back yourself is the cheapest way to find out.

3.1

Read your own words back as the model

Your description reads well to you because you wrote it. The real question is what a model makes of it late in the day, faced with a request nobody planned for.

Overview

Both rows answered: the tool your own words point to, and the row of the description table that made you sure. The two requests differ in who the expense is for.

Detailed steps 5 steps

Reading your own description back as if you were the model is the cheapest way to find a gap in it.

  • Read the first request, which asks only for the status of a report that already exists.
  • Write which tool your words on the description table point to, and which of its four rows made you sure.
  • Read the second request, which files a lodging expense on someone else's behalf.
  • Write which tool it points to, and which row decided it.
  • Change any row of the description table that left you unable to answer with confidence.
Verify each request names both a tool and a deciding row, and that the status-only request points to the status tool rather than to the submission command.

Reflect

Now that this handout is filled in, consider what it would take to hold that line as the expense application grows.

  • Your tool stopped asking the model for things it could not know. Where else in a system like this does a caller get asked for a value only the system can work out?
  • Two of the old tools ran at the same time, and nothing made one wait for the other's answer. What does that suggest about which checks can safely stay separate tools, and which cannot?
  • Every rejection you wrote says whether a report was created. What would someone reasonably do differently because of that one sentence, and what happens when it is missing?
  • Which of your two requests did your tool fail to change the outcome of, and why?

Wrap-up

Noor's hotel expense now has one command behind it that either files the report or says, in plain terms, why it did not — and either way says whether anything was written.

  • One job per tool. Build a tool around the job someone is trying to finish, and the list of checks it needs stops being an argument.
  • Composition is not consolidation. Pull in the checks that one job needs. Leave anything useful on its own as its own tool, and name it in your description.
  • Determinism over cleverness. A check the model is allowed to skip is a check that will get skipped. Put the order in the recipe, where nothing can talk it out of running.
  • Answers that mean something. Say what happened, whether anything was written, and what to do next. A status code leaves the caller guessing.
  • Ordering the checks does not decide who may file. Filing on someone else's behalf stayed possible on every handout in the room, because nothing in this system tracks who is asking. That control belongs somewhere else, and noticing where is the point of the second request.
